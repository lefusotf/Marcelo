# Retos · 0.3 Tu primer proyecto, tu bitácora y Git mínimo

Lección: [00.03-primer-proyecto-git-y-bitacora.md](../00.03-primer-proyecto-git-y-bitacora.md) · Soluciones (**tras tres intentos documentados**): [soluciones](../../../soluciones/M00-entorno-y-metodo/00.03-primer-proyecto-git-y-bitacora-soluciones.md)

**Cómo trabajar**

1. Tu código va en `practica/semana-01/00-03-proyecto/`. Tus commits van en **el repositorio del curso**.
2. Antes de cada commit: `git status`. Antes de cada `git add`: sabes **qué** vas a añadir. **No uses `git add .` a ciegas**.
3. Pistas plegadas: ábrelas una a una y anota cuántas usaste.
4. Mensajes de commit **concretos y en español**.
5. No subas contraseñas, cadenas de conexión ni datos personales reales.

## Nivel 1 · Comprensión

### R-0.3-N1-A · Leer un `.csproj`

**Enunciado.** Este proyecto es distinto del que crea `dotnet new console`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Library</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>disable</ImplicitUsings>
    <Nullable>disable</Nullable>
  </PropertyGroup>
</Project>
```

Explica **línea por línea** qué significa y responde:

1. ¿Qué pasará si ejecutas `dotnet run` en este proyecto?
2. En `Program.cs` hay `Console.WriteLine("x");` sin ninguna línea `using`. ¿Compilará? ¿Qué código de error esperas?
3. ¿Qué dejará de avisarte el compilador por tener `Nullable` desactivado?
4. ¿Qué necesitas tener instalado para **ejecutar** un programa que apunta a `net8.0`, aunque tu SDK sea el 10?

**Criterio.** Explicación correcta de las cuatro líneas y las cuatro respuestas razonadas.

### R-0.3-N1-B · Predecir `git status --short`

**Enunciado.** Escribe qué mostraría `git status --short` en cada situación (el `.gitignore` ya excluye `bin/` y `obj/`). Sé exacto con los espacios y los símbolos.

1. Acabas de crear la carpeta `Saludo` con `dotnet new console -n Saludo` (los archivos son nuevos).
2. Ejecutas `git add Saludo`.
3. Ejecutas `git commit -m "Crea el proyecto Saludo"`.
4. Editas `Saludo/Program.cs`.
5. Ejecutas `git add Saludo/Program.cs` y **después** editas otra vez `Saludo/Program.cs` sin hacer `add`.

**Criterio.** 4 de 5 exactos y para cada uno una frase que diga qué significa.

### R-0.3-N1-C · Mensajes de commit

**Enunciado.** Clasifica cada mensaje como **bueno** o **malo** y explica por qué. Reescribe los malos suponiendo que el cambio real fue el indicado entre paréntesis.

1. `cambios` *(corregiste un error de ortografía en el README)*
2. `Agrega la validación de edad en el reto N3-A`
3. `arreglos varios y además agregué el reto 2 y cambié el .gitignore` *(tres cambios sin relación)*
4. `Corrige el cálculo del impuesto (usaba suma en vez de multiplicación)`
5. `asdf` *(creaste el proyecto del reto N2-A)*
6. `update` *(cambiaste el texto de bienvenida del programa)*

**Criterio.** Clasificación correcta de los seis y reescrituras concretas. Además, explica en una frase por qué el mensaje 3 es un problema de **proceso**, no solo de redacción.

## Nivel 2 · Aplicación

### R-0.3-N2-A · Un proyecto, tres commits

**Enunciado y contexto.** Vas a crear tu primer proyecto y dejar un historial limpio.

**Requisitos funcionales**
1. En `practica/semana-01/00-03-proyecto/` crea el proyecto de consola `Saludo`.
2. **Commit 1:** el proyecto recién creado, sin cambios.
3. Cambia `Program.cs` para que muestre **dos líneas** de bienvenida con tu texto. **Commit 2.**
4. Añade una **tercera línea**. **Commit 3.**
5. Comprueba que `git status` queda limpio y que `bin/` y `obj/` no están en el historial.

**Restricciones técnicas.** Cada commit con un mensaje concreto. Antes de cada `git add`, un `git status` y una lectura. No uses `git add .`: añade la ruta del proyecto o el archivo.

**Entradas y salidas esperadas.** Sin entrada. Salida del programa final: tres líneas con tu texto.

```text
git log --oneline
```
debe mostrar (con tus mensajes y tus hashes) **al menos tres commits** nuevos:
```text
<hash> Agrega la tercera línea de bienvenida
<hash> Muestra dos líneas de bienvenida
<hash> Crea el proyecto Saludo
```

**Casos límite.** (1) Ejecuta `git commit` justo después de otro commit sin cambiar nada: ¿qué responde? (2) Ejecuta `git ls-files practica/semana-01/00-03-proyecto/Saludo`: ¿qué archivos ve Git?

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Un commit guarda lo que está en el área de preparación, no todo lo que cambió.</details>
<details><summary>Pista 2 · método</summary>Ciclo por cada commit: editar → guardar → <code>dotnet run</code> → <code>git status</code> → <code>git add</code> → <code>git commit</code> → <code>git log --oneline</code>.</details>
<details><summary>Pista 3 · localización</summary>Si <code>git status</code> muestra <code>bin/</code> u <code>obj/</code>, algo falla con el <code>.gitignore</code>: comprueba que estás en el repositorio correcto.</details>

**Pruebas**

| N.º | Prueba | Resultado esperado |
|---|---|---|
| 1 | `git log --oneline` | Al menos 3 commits nuevos con mensajes concretos |
| 2 | `git status` | Árbol limpio |
| 3 | `git ls-files <ruta del proyecto>` | Solo `Saludo.csproj` y `Program.cs` |
| 4 | `dotnet run` | Tres líneas de bienvenida |

**Criterios** (rúbrica A): funcional 35 · razonamiento 20 (ciclo de trabajo respetado) · calidad 15 (mensajes) · límites 15 (los dos casos límite) · pruebas/explicación 15.

**Errores frecuentes.** Un solo commit con todo; `git add .` que sube archivos no deseados; olvidar guardar antes de ejecutar.

### R-0.3-N2-B · Tu primera bitácora

**Enunciado y contexto.** Una sesión que no tiene bitácora no cuenta. Escribe la tuya.

**Requisitos funcionales.** Crea `progreso/bitacora/AAAA-MM-DD_sesion-NN.md` (con tus datos reales) a partir de [plantillas/bitacora-de-sesion.md](../../../plantillas/bitacora-de-sesion.md) y complétala:
- Duración real y modo.
- Ejercicios con su **autonomía** (A/B/C/D).
- Al menos **dos predicciones** y su resultado.
- Ayudas usadas.
- Un repaso sin apuntes de tres preguntas.
- El **cierre de cinco puntos**, honesto y concreto.

**Restricciones técnicas.** Sin copiar texto de otra bitácora. "Estudié 0.3" no es un punto concreto: indica qué.

**Entradas y salidas esperadas.** Un archivo Markdown completo, confirmado con un commit de mensaje claro.

**Casos límite.** ¿Qué pones en "Qué pude resolver por mi cuenta" si no resolviste nada sin ayuda? (Respuesta honesta, no vacía.)

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>La bitácora sirve para retomar mañana sin perder el hilo y para detectar tus patrones de error. Escríbela para ti dentro de un mes.</details>
<details><summary>Pista 2 · método</summary>Escribe el cierre al final del bloque 4 con los ejercicios a mano, no de memoria al día siguiente.</details>

**Pruebas.** Los cinco puntos del cierre están completos; cada ejercicio tiene autonomía; hay un commit.

**Criterios.** Funcional 35 (completa) · razonamiento 20 (puntos concretos) · calidad 15 · límites 15 (honestidad en lo no resuelto) · pruebas/explicación 15.

**Errores frecuentes.** Puntos genéricos; no anotar las pistas usadas; omitir el punto 5 (no sabrás por dónde seguir).

## Nivel 3 · Resolución independiente

### R-0.3-N3-A · Ficha de estudio con historial limpio

**Enunciado y contexto.** Un programa que imprime tu plan de estudio y calcula las horas.

**Requisitos funcionales**
1. Crear el proyecto `FichaEstudio` en `practica/semana-01/00-03-proyecto/`.
2. Guardar en variables: sesiones por semana (6), horas por sesión (2) y semanas del plan (28).
3. Calcular las horas por semana y las horas totales.
4. Mostrar exactamente:

```text
===== FICHA DE ESTUDIO =====
Sesiones por semana: 6
Horas por sesión: 2
Horas por semana: 12
Semanas del plan: 28
Horas totales: 336
```

5. Historial de Git con **al menos 4 commits**: creación, datos, cálculos y formato final.

**Restricciones técnicas.** Solo `int`. Ningún resultado escrito a mano. Cada número de entrada aparece una vez.

**Entradas y salidas esperadas.** Sin entrada; salida como arriba.

**Casos límite.** Cambia los datos y comprueba **sin tocar más código**:
- `semanas = 24` → `Horas totales: 288`.
- `sesiones = 5` (con 28 semanas) → `Horas por semana: 10` y `Horas totales: 280`.

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Dos de las líneas de la ficha se calculan; las demás se muestran. Distingue cuáles.</details>
<details><summary>Pista 2 · método</summary>Haz primero la tabla de variables y fórmulas en papel; luego el commit de los datos; luego el de los cálculos.</details>
<details><summary>Pista 3 · localización</summary>Si «Horas totales» te da un valor extraño, revisa si multiplicas lo que debes (horas por semana por semanas).</details>

**Pruebas**

| N.º | Datos | `Horas por semana` | `Horas totales` |
|---|---|---|---|
| 1 | 6 · 2 · 28 | 12 | 336 |
| 2 | 6 · 2 · 24 | 12 | 288 |
| 3 | 5 · 2 · 28 | 10 | 280 |
| 4 | 1 · 1 · 1 | 1 | 1 |

**Criterios** (rúbrica A): funcional 35 · razonamiento 20 · calidad 15 (nombres y commits) · límites 15 (pruebas 2–4) · pruebas/explicación 15.

**Errores frecuentes.** Calcular las horas totales con sesiones por semanas (olvidar las horas por sesión); hacer un único commit; escribir `12` a mano.

### R-0.3-N3-B · `git init` en una carpeta de ensayo

**Enunciado y contexto.** Ya usas un repositorio existente. Ahora crearás uno desde cero para entender de dónde sale todo.

**Requisitos funcionales.** **Fuera** del repositorio del curso (por ejemplo `C:\EnsayoGit`):
1. Crea la carpeta y ejecuta `git init`.
2. Crea `notas.txt` con una línea. Haz un commit.
3. Cambia el archivo (añade una segunda línea). Mira el cambio con `git diff` **antes** de confirmarlo y copia lo que ves.
4. Haz un segundo commit.
5. Muestra el historial con `git log --oneline`.
6. Ejecuta `git status` en una carpeta que **no** sea un repositorio y anota el mensaje.
7. Borra la carpeta de ensayo cuando termines (comprobando antes que es la correcta).

**Restricciones técnicas.** **No** hagas `git init` dentro del repositorio del curso (crearías un repositorio dentro de otro, que es una fuente de confusión).

**Entradas y salidas esperadas.** Capturas (copiadas de la terminal) de `git status`, `git diff`, `git log --oneline` y del mensaje de error de la carpeta sin repositorio.

**Casos límite.** ¿Qué verías con `git log` justo después de `git init`, sin ningún commit?

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary><code>git init</code> crea una carpeta oculta <code>.git</code> que contiene todo el historial; ese es el repositorio.</details>
<details><summary>Pista 2 · método</summary>Cada commit exige que hayas hecho <code>add</code>. Y necesita tu identidad configurada.</details>

**Pruebas.** `git log --oneline` muestra 2 commits · `git diff` mostró la línea añadida con `+` · el error de "no es un repositorio" lo anotaste con tus palabras.

**Criterios.** Funcional 35 · razonamiento 20 · calidad 15 · límites 15 (el caso `git log` sin commits) · pruebas/explicación 15 (explicas qué es `.git`).

**Errores frecuentes.** Hacer `git init` en la carpeta de usuario o en el repositorio del curso; confundir la carpeta oculta `.git` con un archivo del proyecto; borrar la carpeta equivocada.

## Nivel 4 · Integración y transferencia

### R-0.3-N4-A · Rompí mi programa: recuperar la versión buena

**Enunciado y contexto.** Un cambio descuidado dejó un programa sin compilar y ya está en el historial. Debes localizarlo y recuperar el archivo bueno **sin borrar historial**.

**Preparación.** Parte de tu proyecto `Saludo` del reto N2-A (con sus tres commits).

**Requisitos funcionales**
1. **Rompe el programa a propósito:** edita `Program.cs` quitando un `;` y haz commit con el mensaje `Cambia el saludo` **sin compilar antes**.
2. Haz otro commit con un cambio **sin relación** (por ejemplo, una línea nueva en un archivo de texto de `notas`).
3. Ejecuta `dotnet build` y comprueba que **falla**. Anota el código de error.
4. Con `git log --oneline` y `git diff` entre commits, **localiza** cuál commit rompió el programa.
5. **Recupera** `Program.cs` tal como estaba en el último commit bueno **sin tocar los demás archivos**.
6. Comprueba que compila y ejecuta, y haz un commit nuevo que explique lo ocurrido.
7. Explica por qué no usaste `git reset --hard`.

**Restricciones técnicas.** El historial queda con **todos** los commits, incluidos el roto y el de la reparación. No reescribas historia. Solo se restaura el archivo roto.

**Entradas y salidas esperadas.** `git log --oneline` final con (de más reciente a más antiguo): el commit de reparación, el commit sin relación, el roto y los tres anteriores. `dotnet run` funciona.

**Casos límite.** (1) Antes del paso 5, deja un cambio **sin confirmar** en otro archivo: debe seguir ahí después de restaurar. (2) ¿Qué pasaría si usaras `git restore` sobre un archivo con cambios que sí querías conservar?

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Git guarda cada versión del archivo. Un commit se puede nombrar por su <em>hash</em> o por su posición relativa (<code>HEAD~1</code>, <code>HEAD~2</code>).</details>
<details><summary>Pista 2 · método</summary>Para ver qué cambió entre dos commits, <code>git diff &lt;a&gt; &lt;b&gt; -- ruta</code>. Para localizar el roto, compila en cada punto buscando el primero que falla.</details>
<details><summary>Pista 3 · localización</summary>Existe una forma de traer un archivo de otro commit sin cambiar de rama ni tocar el resto: busca <code>git restore --source</code> en la documentación.</details>

**Pruebas**

| N.º | Prueba | Resultado esperado |
|---|---|---|
| 1 | `dotnet build` tras el commit roto | `CS1002` y no compila |
| 2 | `git log --oneline` final | Contiene los 3 commits originales + roto + sin relación + reparación |
| 3 | `dotnet run` final | Funciona |
| 4 | El cambio no confirmado de otro archivo | Sigue presente |

**Criterios.** Funcional 35 · razonamiento 20 (método para localizar el commit) · calidad 15 (mensaje de reparación claro) · límites 15 (los dos casos) · pruebas/explicación 15 (explicas por qué no reescribir historia).

**Errores frecuentes.** `git reset --hard` (destruye trabajo no confirmado y reescribe lo que ves); restaurar todo el árbol en vez de un archivo; confirmar la reparación sin compilar.
