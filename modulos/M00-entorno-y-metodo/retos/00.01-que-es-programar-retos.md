# Retos · 0.1 Qué es programar y cómo funciona un programa

Lección: [00.01-que-es-programar.md](../00.01-que-es-programar.md) · Soluciones (**no abrir antes de tres intentos documentados**): [soluciones](../../../soluciones/M00-entorno-y-metodo/00.01-que-es-programar-soluciones.md)

**Cómo trabajar los retos**

1. Respeta el orden: Nivel 1 → 2 → 3 → 4. No saltes niveles.
2. Escribe tú todo el código. En los retos de predicción, **predice por escrito antes de ejecutar**.
3. Las pistas están plegadas: ábrelas **una a una**, solo después de intentar. Anota cuántas usaste.
4. Registra cada reto en tu bitácora con su autonomía (A sin ayuda · B hasta 2 pistas · C pista fuerte · D solución).
5. Los decimales pueden salir con coma en tu equipo; los retos de esta unidad usan solo enteros.

## Nivel 1 · Comprensión

*(Formato condensado: no hay requisitos funcionales ni salidas propias, porque se trata de reconocer, ordenar, predecir y explicar.)*

### R-0.1-N1-A · Clasificar errores

**Enunciado.** Para cada situación indica: (1) **en qué momento** aparece el problema (al compilar, al ejecutar o al revisar el resultado), (2) **qué tipo de error** es, y (3) **qué verías** (mensaje, caída o resultado equivocado).

1. Olvidas cerrar unas comillas de un texto.
2. Un programa calcula el promedio de 7, 8 y 8 y muestra `7` en vez de `7.67`.
3. Escribes `Console.Writeline("hola");` (con la `l` minúscula).
4. Un programa pide un número, la persona escribe `abc` y el programa se cae con `FormatException`.
5. Un programa que calcula la edad muestra `-5` porque restaste los años al revés.
6. Escribes `int x = 5.5;`

**Cómo verificarlo.** Para 1, 3 y 6 puedes **comprobarlo** escribiéndolos en un proyecto (cuando completes la unidad 0.2) y leyendo el código `CSxxxx`. Los demás se razonan.
**Criterio.** 5 de 6 con el momento y el tipo correctos, y razonando **por qué**.

### R-0.1-N1-B · Ordenar el recorrido

**Enunciado.** Estos siete elementos están desordenados. Ordénalos del primero al último y marca cuáles son **acciones** (algo que se hace) y cuáles **productos** (algo que existe):

- A. Archivo `.dll` con lenguaje intermedio (IL)
- B. Código de máquina
- C. `Program.cs`
- D. El compilador revisa sintaxis y tipos y traduce a IL
- E. El JIT traduce IL a código de máquina
- F. La CPU ejecuta las instrucciones
- G. El resultado se muestra en la consola

**Criterio.** Orden correcto y clasificación correcta; además explica en una frase por qué el compilador no produce directamente código de máquina en .NET.

### R-0.1-N1-C · Predecir la salida

**Enunciado.** Escribe **por escrito** qué mostrará cada programa. **No los ejecutes hasta haber escrito las tres predicciones.** Después ejecútalos y anota si acertaste y, si no, por qué.

Programa 1:
```text
Console.WriteLine(2 + 3 * 4);
Console.WriteLine((2 + 3) * 4);
Console.WriteLine("2 + 3 * 4");
```

Programa 2:
```text
int a = 10;
int b = 3;
a = a + b;
b = a - b;
Console.WriteLine(a);
Console.WriteLine(b);
```

Programa 3:
```text
Console.Write("Hola ");
Console.WriteLine("mundo");
Console.Write("Adiós");
Console.WriteLine();
Console.WriteLine("Fin");
```

**Criterio.** Aciertas las tres **antes** de ejecutar. Para el Programa 2 incluye una tabla con el valor de `a` y de `b` tras cada línea.

### R-0.1-N1-D · Explicar código

**Enunciado.** Explica este programa **línea por línea** con tus palabras (no repitas el código en voz alta). Después: (1) haz la tabla de valores, (2) di qué mostraría si `envio` valiera `0`, y (3) di qué cambiarías para que el total incluyera dos pedidos iguales.

```text
int cantidad = 5;
int precioUnitario = 4;
int envio = 3;
int subtotal = cantidad * precioUnitario;
int total = subtotal + envio;
Console.WriteLine("Subtotal: " + subtotal);
Console.WriteLine("Total: " + total);
```

**Criterio.** Explicación correcta de las siete líneas, tabla correcta y las dos respuestas razonadas.

## Nivel 2 · Aplicación

### R-0.1-N2-A · Modificar el programa del área

**Enunciado y contexto.** Tienes el programa del área de un rectángulo de la lección. Debes ampliarlo para que muestre más información sin cambiar su estructura básica.

Punto de partida (escríbelo tú):
```text
int ancho = 8;
int alto = 3;
int area = ancho * alto;
Console.WriteLine("El área es: " + area);
```

**Requisitos funcionales**
1. Mostrar primero una línea con las dimensiones: `Rectángulo de 8 x 3` (usando las **variables**, no los números escritos a mano).
2. Mostrar el área: `Área: 24`.
3. Mostrar el perímetro: `Perímetro: 22`.
4. Mostrar el área del triángulo con esa misma base y altura: `Área del triángulo: 12`.

**Restricciones técnicas.** Solo enteros; sin leer datos del usuario; los números `8` y `3` aparecen **una sola vez** cada uno en el programa.

**Entradas y salidas esperadas** (los datos se cambian en el código):

| `ancho` | `alto` | Salida |
|---|---|---|
| 8 | 3 | `Rectángulo de 8 x 3` · `Área: 24` · `Perímetro: 22` · `Área del triángulo: 12` |
| 5 | 5 | `Rectángulo de 5 x 5` · `Área: 25` · `Perímetro: 20` · `Área del triángulo: 12` |

**Ejemplo de ejecución** (primer juego de datos):
```text
Rectángulo de 8 x 3
Área: 24
Perímetro: 22
Área del triángulo: 12
```

**Casos límite.** Cambia los valores y comprueba que **toda** la salida se actualiza. Fíjate en el segundo juego: el triángulo de 5 × 5 da `12`, no `12.5`. Anota **por qué** en tu bitácora.

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Si alguna línea muestra un número que escribiste a mano en lugar de una variable, al cambiar los datos esa línea quedará desactualizada.</details>
<details><summary>Pista 2 · método</summary>Antes de programar, escribe cada resultado como fórmula con los nombres de las variables (por ejemplo, perímetro = 2 por la suma de los dos lados). Después tradúcela.</details>
<details><summary>Pista 3 · localización</summary>Para la primera línea necesitas unir texto y números varias veces con <code>+</code>; revisa dónde van los espacios dentro de las comillas.</details>

**Pruebas con las que verificar.** Las dos filas de la tabla anterior; además `ancho = 1`, `alto = 1` (triángulo `0`) y `ancho = 10`, `alto = 4` (`Área: 40`, `Perímetro: 28`, triángulo `20`).

**Criterios de evaluación** (rúbrica A de [RUBRICAS.md](../../../evaluaciones/RUBRICAS.md)): funcional 35 · razonamiento 20 (fórmulas escritas antes) · calidad 15 (nombres, sin números repetidos) · límites 15 (probaste los 4 juegos de datos) · pruebas/explicación 15 (la tabla de pruebas y el porqué del `12`).

**Errores frecuentes.** Escribir `8 x 3` a mano en la primera línea; `2 * ancho + alto` en vez de `2 * (ancho + alto)`; olvidar un espacio dentro de las comillas.

### R-0.1-N2-B · Completar un programa

**Enunciado y contexto.** Una cafetería necesita calcular la cuenta de una mesa. El programa está a medias: los huecos `___` son lo que debes escribir. No cambies nada de lo que ya está.

```text
int cafes = 3;
int precioCafe = ___;          // cada café cuesta 2
int panes = ___;               // se pidieron 4 panes
int precioPan = 1;

int totalCafes = cafes * ___;
int totalPanes = ___ * precioPan;
int cuenta = totalCafes ___ totalPanes;

Console.WriteLine("Cuenta: " + ___);
```

**Requisitos funcionales.** Que el programa compile y muestre exactamente `Cuenta: 10`.

**Restricciones técnicas.** Solo se rellenan los huecos (seis en total). No se añaden líneas.

**Entradas y salidas esperadas.** Sin entrada. Salida: `Cuenta: 10`.

**Casos límite.** Cambia `panes` a `0`: la cuenta debe ser `6`. Cambia `cafes` a `0`: debe ser `4`.

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Los comentarios (<code>//</code>) del final de la línea te dicen qué dato falta. Un comentario no se ejecuta: es una nota para quien lee.</details>
<details><summary>Pista 2 · método</summary>Lee el programa de abajo hacia arriba: ¿qué necesita la última línea? ¿De dónde sale ese valor?</details>

**Pruebas.** `Cuenta: 10` (original) · `panes = 0` → `Cuenta: 6` · `cafes = 0` → `Cuenta: 4`.

**Criterios.** Funcional 35 (compila y da `10`) · razonamiento 20 (anotaste qué representa cada hueco) · calidad 15 · límites 15 (las dos pruebas extra) · pruebas/explicación 15.

**Errores frecuentes.** Escribir el número `10` directamente en el último hueco (la cuenta no se calcula); confundir el nombre de la variable de los totales; usar `-` o `*` en el hueco del operador.

### R-0.1-N2-C · El robot literal (algoritmo sin código)

**Enunciado y contexto.** Un robot **literal** va a ejecutar tu algoritmo con papel y lápiz. Solo entiende operaciones básicas (leer un dato, sumar, dividir, comparar, escribir un resultado) y **hace exactamente lo que dice cada paso**. No adivina nada.

**Problema.** Dadas las tres notas de un estudiante, calcular su promedio y escribir `Aprueba` si el promedio es **6 o más**, o `Reprueba` en caso contrario.

**Requisitos funcionales**
1. Escribir el algoritmo en **pasos numerados** en lenguaje natural (no en C#).
2. Cada paso debe indicar **qué datos usa** y **qué produce**.
3. El algoritmo debe terminar en un número finito de pasos.
4. Ejecutarlo "a mano" como el robot con **tres juegos de datos** y mostrar la traza.

**Restricciones técnicas.** Prohibidas las frases ambiguas: "más o menos", "si hace falta", "revisar", "hacer el cálculo".

**Entradas y salidas esperadas**

| Notas | Promedio | Salida |
|---|---|---|
| 7, 5, 8 | 6.67 | `Aprueba` |
| 4, 5, 6 | 5 | `Reprueba` |
| 6, 6, 6 | 6 | `Aprueba` |

**Casos límite.** El promedio exactamente 6 (¿lo cubre tu condición?).

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Pregúntate: ¿qué entra, qué se hace, qué sale? Empieza escribiendo las tres respuestas.</details>
<details><summary>Pista 2 · método</summary>Cada paso debería poder ejecutarse sin que el robot tenga que decidir cómo hacerlo.</details>
<details><summary>Pista 3 · localización</summary>Si una traza te lleva a un paso donde el robot "no sabe qué hacer", ese paso es ambiguo: reescríbelo.</details>

**Pruebas.** Las tres filas. Si quieres, pide al instructor que actúe como robot literal en un intercambio de mensajes: dices el paso y él responde solo con lo que ese paso dice.

**Criterios.** Funcional 35 (el robot llega al resultado correcto en los tres casos) · razonamiento 20 · calidad 15 (pasos numerados y sin ambigüedad) · límites 15 (el promedio exacto 6) · pruebas/explicación 15 (las tres trazas).

**Errores frecuentes.** Olvidar dividir entre 3; comparar con "mayor que 6" (deja fuera al 6); mezclar el cálculo con la decisión en el mismo paso.

## Nivel 3 · Resolución independiente

### R-0.1-N3-A · Recibo de compra

**Enunciado y contexto.** Una papelería necesita un programa que imprima el recibo de una compra. Los datos de la compra están en el programa (por ahora no se leen del teclado).

**Requisitos funcionales**
1. Guardar en variables las cantidades y los precios: cuaderno (4 unidades a 5), lápiz (10 unidades a 1), carpeta (2 unidades a 10).
2. Calcular el total de cada línea, el **subtotal**, el **impuesto del 10 %** (calculado, no escrito a mano) y el **total**.
3. Mostrar exactamente este formato:

```text
===== RECIBO =====
Cuaderno: 4 x 5 = 20
Lápiz: 10 x 1 = 10
Carpeta: 2 x 10 = 20
Subtotal: 50
Impuesto (10%): 5
Total: 55
```

**Restricciones técnicas.** Solo `int`; sin leer del teclado; cada número (cantidad o precio) aparece **una sola vez** en el código; ningún resultado se escribe a mano.

**Entradas y salidas esperadas.** Sin entrada. Salida: la del formato anterior.

**Casos límite.** Cambia la cantidad de cuadernos a `6`: el programa debe dar subtotal `60`, impuesto `6`, total `66` **sin tocar nada más**. Cambia una cantidad a `0`: esa línea debe mostrar `0`.

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Antes de escribir una línea de código, escribe en papel qué variables necesitas y qué fórmulas las relacionan.</details>
<details><summary>Pista 2 · método</summary>Haz una tabla de variables: nombre, valor inicial, de dónde sale. Después recorre el recibo de arriba abajo.</details>
<details><summary>Pista 3 · localización</summary>Si tu impuesto te da un valor extraño, revisa el orden de las operaciones y qué multiplicas por qué.</details>

**Pruebas**

| N.º | Cambio | Salida esperada (líneas finales) |
|---|---|---|
| 1 | Datos del enunciado | `Subtotal: 50` · `Impuesto (10%): 5` · `Total: 55` |
| 2 | Cuadernos = 6 | `Cuaderno: 6 x 5 = 30` · `Subtotal: 60` · `Impuesto (10%): 6` · `Total: 66` |
| 3 | Carpetas = 0 | `Carpeta: 2 x 10 = 20` pasa a `Carpeta: 0 x 10 = 0` · `Subtotal: 30` · `Impuesto (10%): 3` · `Total: 33` |

**Criterios de evaluación** (rúbrica A): funcional 35 · razonamiento 20 (tabla de variables previa) · calidad 15 (nombres claros) · límites 15 (pruebas 2 y 3) · pruebas/explicación 15 (explicas tu fórmula del impuesto).

**Errores frecuentes.** Escribir `5` a mano en una línea; calcular el impuesto sobre un solo producto; `subtotal * 10 / 100` frente a `subtotal / 100 * 10` (compara el resultado con un subtotal que no sea múltiplo de 100 y explica la diferencia).

### R-0.1-N3-B · Fabrica tus propios errores

**Enunciado y contexto.** Ya sabes reconocer los tres tipos de error. Ahora los provocas a propósito para aprender a leerlos.

**Requisitos funcionales.** Escribe **tres programas pequeños** (máximo 8 líneas), cada uno con **un solo** error de un tipo distinto:
1. Uno que **no compile**, con un código `CSxxxx` **distinto** de los de la lección (`CS1002`, `CS0103`, `CS1010`, `CS0841`, `CS0020`).
2. Uno que **compile pero se caiga** al ejecutar, con una excepción **distinta** de `DivideByZeroException`.
3. Uno que **compile y corra** pero muestre un resultado **equivocado**.

Para cada uno documenta: el código, el mensaje o la salida real, la línea afectada, la causa y la corrección.

**Restricciones técnicas.** Sin leer del teclado. Los errores deben ser genuinos (no un comentario que diga "aquí hay un error").

**Entradas y salidas esperadas.** Un archivo de documentación con las tres secciones y las salidas **reales** copiadas de tu consola.

**Casos límite.** El error de ejecución debe ocurrir en tiempo de ejecución y no en compilación: comprueba que el compilador no lo detecta.

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Para el error de compilación: ¿qué otras reglas del lenguaje conoces? (tipos, nombres, paréntesis…)</details>
<details><summary>Pista 2 · método</summary>Para el de ejecución, busca en la documentación qué hace el método <code>int.Parse</code> cuando recibe un texto que no es un número.</details>
<details><summary>Pista 3 · localización</summary>El error lógico más sencillo: una fórmula correcta en apariencia con el operador equivocado.</details>

**Pruebas.** Un compañero (o el instructor) debe poder clasificar tus tres programas sin que se los expliques.

**Criterios.** Funcional 35 (cada programa se comporta como se afirma) · razonamiento 20 (causa y corrección bien explicadas) · calidad 15 · límites 15 (el error de ejecución no es de compilación) · pruebas/explicación 15 (salidas reales copiadas).

**Errores frecuentes.** Un "error lógico" que en realidad no compila; un "error de ejecución" que el compilador detecta; copiar el mensaje de internet en vez de producirlo.

## Nivel 4 · Integración y transferencia

### R-0.1-N4-A · Un programa que no escribiste

**Enunciado y contexto.** Un compañero escribió este programa para calcular el pago de un empleado, pero no funciona. No sabes qué pasa. Es tu trabajo arreglarlo **sin reescribirlo entero**.

Escríbelo tal cual en un proyecto de consola y arréglalo:

```text
int horas = 40;
int tarifa = 12;
int diasTrabajados = 0;

int pagoBruto = horas + tarifa;
int pagoPorDia = pagoBruto / diasTrabajados;
Console.WriteLine("Pago bruto: " + pagoBruto)
Console.WriteLine("Pago por día: " + pagoPorDia);
```

**Requisitos funcionales.** Que el programa muestre exactamente:

```text
Pago bruto: 480
Pago por día: 96
```

**Restricciones técnicas.** No cambies la estructura. Cada cambio debe estar justificado. Aplica este método en cada fallo: *leer el mensaje → formular una hipótesis → cambiar **una** cosa → volver a ejecutar*.

**Entradas y salidas esperadas.** Sin entrada. Salida: la de arriba. Los datos reales: 40 horas, 12 de tarifa, 5 días trabajados.

**Casos límite.** Cambia `horas` a `0`: el pago debe ser `0` y no caerse. ¿Qué pasaría si `diasTrabajados` fuera `0` de verdad? Escribe qué harías (no hace falta programarlo).

**Pistas progresivas**
<details><summary>Pista 1 · concepto</summary>Hay tres errores, uno de cada tipo. Aparecerán en orden: no verás el segundo hasta arreglar el primero.</details>
<details><summary>Pista 2 · método</summary>Cuando se caiga, pregúntate no solo "¿en qué línea?", sino "¿de dónde sale el valor que causa la caída?".</details>
<details><summary>Pista 3 · localización</summary>El tercer error no produce ningún mensaje: solo lo detectas comparando tu salida con la esperada.</details>

**Pruebas.** Salida exacta del enunciado · `horas = 0` → `Pago bruto: 0` y `Pago por día: 0`.

**Criterios de evaluación.** Funcional 35 · razonamiento 20 (informe de los tres hallazgos: síntoma → causa → corrección) · calidad 15 (cambios mínimos) · límites 15 (prueba con `horas = 0` y reflexión sobre `diasTrabajados = 0`) · pruebas/explicación 15.

**Errores frecuentes.** Arreglar la caída "quitando la división"; ocultar el síntoma cambiando el valor esperado; corregir el error lógico sin entender por qué `+` no era la operación.
