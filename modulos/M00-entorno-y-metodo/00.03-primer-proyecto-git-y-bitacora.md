## 3. Explicación desde cero

### 3.1 Qué es un proyecto de .NET

Un **proyecto** es una carpeta con (como mínimo) dos cosas:

- Un archivo **`.csproj`** que **describe** el proyecto: qué tipo de programa es, para qué versión de .NET se compila, qué opciones usa.
- Uno o varios archivos de **código** `.cs`.

Al ejecutar `dotnet new console -n Saludo` aparece esto:

```text
Saludo/
├── Saludo.csproj
└── Program.cs
```

El contenido de `Saludo.csproj` (plantilla de .NET 10):

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

| Línea | Significa |
|---|---|
| `Sdk="Microsoft.NET.Sdk"` | Usa las reglas de compilación del SDK de .NET. |
| `OutputType` = `Exe` | El resultado es un programa ejecutable (no una biblioteca). |
| `TargetFramework` = `net10.0` | Se compila para .NET 10. |
| `ImplicitUsings` = `enable` | Se importan automáticamente espacios de nombres comunes (`System`, `System.Linq`…). Por eso `Console` funciona sin `using System;`. |
| `Nullable` = `enable` | El compilador te **avisa** de posibles usos de valores nulos. Son *advertencias* (`CS86xx`), no errores; las aprenderás a entender en el módulo 3. |

**`Program.cs`** contiene el código; en una plantilla nueva es un `Console.WriteLine("Hello, World!");`.

Después de compilar aparecen dos carpetas más:

- **`bin/`**: el resultado de la compilación (el ensamblado `.dll` y los archivos para ejecutarlo). La ruta típica es `bin/Debug/net10.0/`.
- **`obj/`**: archivos intermedios del proceso de compilación.

Ambas se **regeneran** cuando compilas, así que **no se guardan en Git** (el `.gitignore` de este repositorio ya las excluye).

### 3.2 Los comandos de siempre

| Comando | Qué hace |
|---|---|
| `dotnet new console -n Saludo` | Crea una carpeta `Saludo` con un proyecto de consola. |
| `dotnet build` | **Compila** y avisa de errores. No ejecuta nada. Debe lanzarse en la carpeta del proyecto. |
| `dotnet run` | **Compila** (si hace falta) y **ejecuta**. |
| `dotnet clean` | Borra lo compilado. |

La diferencia entre `build` y `run`: `build` solo comprueba que compila; `run` además lo ejecuta. Si hay errores de compilación, `run` no ejecuta nada.

> **Una curiosidad de .NET 10:** un único archivo puede ejecutarse sin proyecto con `dotnet run archivo.cs` (*aplicaciones de un solo archivo*). Es práctico para pruebas rápidas, pero **en el curso trabajamos con proyectos** porque es lo que encontrarás en cualquier empleo.

### 3.3 Cómo se estudia aquí: el método

Esto es "Módulo 0: cómo organizar sesiones de estudio y registrar el progreso". Resumen de lo que ya has visto en el [plan](../../PLAN_DE_ESTUDIO.md) y en las [reglas](../../REGLAS_DE_APRENDIZAJE.md):

1. **Una sesión = cuatro bloques** (20 + 40 + 30 + 30 minutos): leer, programar, retos y depuración, repaso y cierre.
2. **Predecir antes de ejecutar.** Escribe qué crees que saldrá. La diferencia entre tu predicción y la realidad es donde se aprende.
3. **Recuperar de memoria** vale más que releer. El bloque de repaso usa preguntas **sin apuntes** de sesiones anteriores.
4. **Tablas de pruebas** antes de dar un programa por bueno.
5. **Bitácora de cada sesión** con el cierre de cinco puntos:
   1. qué estudié, 2. qué pude resolver por mi cuenta, 3. qué errores cometí, 4. qué debo repasar, 5. qué haré en la próxima sesión.
6. **Sin cierre no cuenta la sesión.** Con él puedes retomar mañana sin perder el hilo.

Estructura de trabajo de este curso (ya creada en el repositorio):

```text
practica/                 ← TU código (tú lo escribes y lo versionas)
  semana-01/
    00-01-fuente/ ...
progreso/bitacora/        ← registro de sesiones (el instructor y tú)
```

### 3.4 Git mínimo: guardar versiones de tu trabajo

**Git** es un sistema de **control de versiones**: guarda el historial de tu trabajo como una serie de **instantáneas** (*commits*), cada una con un mensaje que explica qué cambió. Sirve para volver atrás, comparar, ver qué se hizo y cuándo, y trabajar con otras personas.

Un archivo en un repositorio de Git pasa por tres lugares:

```text
Directorio de trabajo  ──git add──►  Área de preparación (staging)  ──git commit──►  Repositorio (historial)
 (lo que editas)                      (lo que irá en el próximo commit)                (instantáneas guardadas)
```

Comandos mínimos:

| Comando | Qué hace |
|---|---|
| `git status` | Muestra qué archivos cambiaron y cuáles están preparados. **Úsalo antes y después de todo.** |
| `git add ruta` | Prepara un archivo o carpeta para el próximo commit. |
| `git commit -m "mensaje"` | Guarda una instantánea con ese mensaje. |
| `git log --oneline` | Lista el historial resumido (un commit por línea). |
| `git diff` | Muestra los cambios aún no preparados. |
| `git restore ruta` | Descarta cambios no confirmados de un archivo (**irreversible**). |

**Identidad** (se hace una vez por equipo):

```text
git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo@ejemplo.com"
```

Tu nombre y correo quedan en cada commit y se verán si el repositorio es público. Si quieres privacidad, GitHub ofrece un correo "noreply" en su configuración.

**Un buen mensaje de commit** dice *qué cambió* de forma concreta y breve: `Agrega el reto N2-A de la unidad 0.1`. Un mal mensaje: `cambios`, `arreglos`, `asdf`.

**Sincronizar con GitHub.** Si trabajas con un repositorio remoto (como el de este curso), `git pull` trae los cambios del remoto y `git push` envía tus commits. Se explican a fondo en el módulo 7 (unidad 7.3); por ahora basta con saber que **un commit solo vive en tu equipo hasta que haces `push`**.

## 4. Analogía intuitiva

- **El proyecto** es una maleta con una etiqueta (`.csproj`) que dice qué lleva y a dónde va. `bin` y `obj` son las virutas que deja el taller: útiles mientras trabajas, pero no se guardan.
- **Git** son las *partidas guardadas* de un videojuego: puedes volver a cualquier punto. El *área de preparación* es el carrito de la compra: eliges qué entra en el próximo guardado antes de pasar por caja (`commit`).

**Dónde falla:** un videojuego guarda *todo*; Git guarda solo lo que **tú** añades al carrito, y solo cuando haces el commit. Un archivo modificado y no confirmado no está a salvo.

## 5. Ejemplos comentados

### Ejemplo 1 · Crear, compilar y ejecutar

```text
dotnet new console -n Saludo
cd Saludo
dotnet build
dotnet run
```

`dotnet build` termina con un resumen como este (el formato exacto cambia según la versión y el terminal):

```text
Build succeeded.
    0 Warning(s)
    0 Error(s)
```

Y `dotnet run` muestra `Hello, World!`.

### Ejemplo 2 · Hacer que el programa diga algo tuyo

Abre `Program.cs` y sustituye su contenido:

<!--v
modo: ejecuta
salida: siguiente
-->
```csharp
Console.WriteLine("Hola, soy un programa de consola.");
Console.WriteLine("Estoy en un proyecto de .NET.");
```

```text
Hola, soy un programa de consola.
Estoy en un proyecto de .NET.
```

**Guarda el archivo** (`Ctrl + S`) antes de ejecutar. Si no guardas, `dotnet run` compila la versión anterior y creerás que tu cambio no funciona. En Visual Studio y VS Code se puede activar el guardado automático.

### Ejemplo 3 · Una sesión mínima de Git

Se hizo en una carpeta temporal con Git 2.43. Los códigos hexadecimales (los *hashes*) serán distintos en tu equipo.

```text
git init
```
Crea un repositorio en la carpeta actual. *(En este curso tu repositorio ya existe: no hace falta repetirlo ahí; se practica en un reto, en una carpeta de ensayo.)*

```text
git status
```
```text
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

Tras crear el proyecto `Saludo`, `git status --short` muestra `?? Saludo/` (el signo `??` significa *no seguido por Git*). Si **no** hay `.gitignore`, `bin/` y `obj/` aparecerían dentro. Con un `.gitignore` que contenga `bin/` y `obj/`, solo se ven los archivos que importan. Preparamos y confirmamos:

```text
git add .gitignore Saludo
git status --short
```
```text
A  .gitignore
A  Saludo/Program.cs
A  Saludo/Saludo.csproj
```
```text
git commit -m "Crea el proyecto Saludo"
git log --oneline
```
```text
637b79a Crea el proyecto Saludo
```

Si modificas `Program.cs`, `git status --short` muestra ` M Saludo/Program.cs` (la `M` está en la segunda columna: *modificado, sin preparar*), y `git diff` enseña línea por línea qué cambió.

### Ejemplo 4 · Volver a una versión anterior de un archivo

Tras dos commits (`Crea el proyecto Saludo` y `Agrega un comentario`), `git log --oneline` muestra:

```text
28f3c3d Agrega un comentario
637b79a Crea el proyecto Saludo
```

Para traer la versión de `Program.cs` del commit anterior (`HEAD~1` es "un commit antes del actual"):

```text
git restore --source=HEAD~1 -- Saludo/Program.cs
```

El archivo recupera su contenido anterior, pero **Git lo ve como una modificación** respecto al último commit (` M Saludo/Program.cs`), porque el historial no se reescribe: si te convence, lo confirmas con un nuevo commit. **Esto es la gracia de Git: nada se pierde mientras esté en un commit.**

### Ejemplo 5 · Una entrada de bitácora (ficticia)

```text
# Sesión 03 · 2026-10-16 · Unidad 0.3
- Estudié: anatomía de un proyecto, build vs run, Git mínimo.
- Resolví solo: N1-A, N1-B, N2-A (autonomía A). N2-B con una pista de método (B).
- Errores: olvidé guardar Program.cs antes de ejecutar y creí que el cambio no funcionaba.
- Repasar: diferencia entre git add y git commit (la confundí en el repaso).
- Próxima sesión: unidad 0.4, empezar por el repaso de git add/commit.
```

## 6. Análisis del código

Qué hace `dotnet run` por dentro, paso a paso:

1. **Restaurar** (*restore*): comprueba que están todas las dependencias del proyecto y las descarga si faltan. En un proyecto nuevo sin paquetes extra es casi instantáneo.
2. **Compilar** (*build*): el compilador lee `Program.cs`, valida la sintaxis y los tipos, y genera `bin/Debug/net10.0/Saludo.dll`. Si hay errores, **aquí se detiene**.
3. **Ejecutar**: el runtime carga el `.dll`, el JIT lo convierte a código de máquina y se ejecuta el programa.

Estados de un archivo en Git:

| Situación | Cómo se ve en `git status --short` | Siguiente paso |
|---|---|---|
| Archivo nuevo sin seguimiento | `?? Saludo/` | `git add` |
| Nuevo y preparado | `A  Saludo/Program.cs` | `git commit` |
| Existente y modificado, sin preparar | ` M Saludo/Program.cs` | `git add` |
| Existente, modificado y preparado | `M  Saludo/Program.cs` | `git commit` |
| Sin cambios | *(nada)* | — |

## 7. Errores frecuentes

| Síntoma | Causa | Corrección |
|---|---|---|
| `MSB1003: Specify a project or solution file…` al hacer `dotnet build` | No estás en la carpeta del proyecto. | `pwd`, `ls`, `cd` al proyecto. |
| Cambias el código y no cambia la salida | No guardaste el archivo. | Guardar (`Ctrl + S`) o activar el guardado automático. |
| `git commit -m "…"` responde `no changes added to commit` | No hiciste `git add`. | `git add ruta` y repetir. |
| `git commit` sin `-m` abre un editor extraño (a menudo **vim**) y no sabes salir | Git abre el editor para el mensaje. | Para salir sin guardar en vim: `Esc`, luego `:q!` y Enter. Mejor: usa siempre `-m`. |
| `Author identity unknown` / `Please tell me who you are` | No configuraste `user.name` y `user.email`. | Los comandos `git config --global …` de arriba. |
| Aparecen `bin/` y `obj/` en `git status` | Falta el `.gitignore`. | Usa el del repositorio (raíz) o crea uno; no los confirmes. |
| Mensajes de commit como `cambios` o `asdf` | Prisa. | Mensaje concreto: *qué cambió*. |
| Un commit gigante con 20 archivos distintos | Acumulaste mucho trabajo. | Commits pequeños, uno por idea. |
| `git restore` borró cambios que querías | Descarta cambios no confirmados y **no se puede deshacer**. | Haz commit antes de experimentar; usa `git diff` para mirar primero. |
| Subiste una contraseña o cadena de conexión real | Los secretos no deben vivir en el repositorio. | No los confirmes. Si ya ocurrió, hay que **rotar** la credencial (borrar el archivo no basta: el historial la conserva). Se aborda en el módulo 6. |

## 8. Variaciones

- **Visual Studio.** *Archivo → Nuevo → Proyecto → Aplicación de consola*. Crea el mismo `.csproj` y un archivo de solución (`.sln` o `.slnx`) que agrupa proyectos; por ahora, ignóralo. `F5` ejecuta con depurador; `Ctrl + F5` sin depurador.
- **VS Code.** Abre la carpeta del proyecto; el comando *.NET: New Project* o la terminal integrada con `dotnet new console` dan el mismo resultado.
- **Estructura clásica.** `dotnet new console --use-program-main` genera una clase `Program` con un método `Main` explícito en vez de sentencias de nivel superior.
- **Otra versión de .NET.** `dotnet new console -f net8.0` apunta a otra versión; para el curso se usa `net10.0`.
- **Aplicación de un solo archivo.** `dotnet run archivo.cs` (verificado con SDK 10).
